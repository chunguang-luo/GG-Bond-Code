# NextCode 项目架构文档

> 最后更新：2026-05-29

## 一、项目概览

**NextCode** 是一个 AI 驱动的 CLI 助手（v0.3.0），采用 **双进程架构**：Python 后端负责 LLM 编排、工具执行、权限管理和上下文管理；Node.js/React 前端通过 Ink 框架提供富终端 UI。两端通过 **Unix Domain Socket** 以 JSON-Line 协议通信。

| 维度 | 选型 |
|------|------|
| 后端语言 | Python 3.13 + asyncio |
| CLI 框架 | Click |
| 数据校验 | Pydantic（Tool schema 生成 + 参数验证） |
| 前端框架 | React 18 + Ink 5 + TypeScript |
| 进程通信 | Unix Domain Socket (`/tmp/nextcode-ipc-{pid}.sock`) |
| 消息协议 | JSON-Line（每行一个 JSON 对象） |
| 构建工具 | hatchling (Python) + esbuild (Node.js) |

```
|  +-- CompactManager                      |  compact.*    |  +-- PermissionDialog|

|  Transport (Server)                      |  task.*        |  Transport (Client)  |

+------------------------------------------+                +----------------------+
```

| -> 前端 | `query.tool_use` | 工具调用详情 |

| -> 前端 | `query.complete` | 对话轮完成 |
| -> 前端 | `query.error` | 错误 |
| -> 前端 | `permission.request` | 权限确认请求 |
| -> 前端 | `compact.started` | 压缩开始 |
| -> 前端 | `compact.complete` | 压缩完成 |
| -> 前端 | `context.info` | 上下文窗口信息 |

## 五、状态管理

### 5.1 核心组件

| 组件 | 文件 | 职责 |
|------|------|------|
| `_Store` | `state/store.py` | 全局单例 KV Store，支持 subscribe/onChange/snapshot/reset |
| `ToolUseContext` | `state/context.py` | 每次工具执行的运行时上下文容器 |
| `LoopState` | `state/transition.py` | 对话循环状态机 + 14 种 TransitionReason |

### 5.2 Store 架构

```
setup() 初始化
  │
  ├─ reset_store(on_change=_on_store_change)   → 全局单例
  ├─ Store ← Settings (加载默认值)
  └─ Store → Settings (onChange 自动同步持久化 key)
       │
       ├─ 创建主循环上下文          ├─ 创建子 Agent 上下文
       │  create_store_context()    │  create_subagent_context()
       │                            │
       ├─ get_state → Store.get    ├─ get_state → Store.get (只读)
       ├─ set_state → Store.set    ├─ set_state → no-op (隔离)
       └─ set_state_for_tasks      └─ set_state_for_tasks → 穿透到根 Store
```

### 5.3 Store Key 清单

| Key | 写入方 | 读取方 | 是否持久化 |
|-----|--------|--------|-----------|
| `cwd` | setup.py | query.py, prefetch.py, agents/runner.py | ❌ |
| `model` | setup.py | query.py, agents/runner.py | ✅ (唯一持久化 key) |
| `project_root` | setup.py | config/settings.py | ❌ |
| `messages` | setup.py, query.py | query.py, agents/runner.py | ❌ |
| `session_start` | setup.py | — | ❌ |
| `ui.show_thinking` | setup.py | — | ❌ |
| `ui.show_tool_details` | setup.py | — | ❌ |
| `omit_git_status` | agents/runner.py | query.py | ❌ |
| `omit_nextcode_md` | agents/runner.py | query.py | ❌ |

### 5.4 ToolUseContext 数据结构

```
ToolUseContext (dataclass)
  ├─ get_state: Callable[[str], Any]         ← 读状态（始终读真实数据）
  ├─ set_state: Callable[[str, Any], None]   ← 写状态（子 Agent 可为 no-op）
  ├─ set_state_for_tasks: Callable | None    ← 始终穿透到根 Store
  ├─ permissions: PermissionManager          ← 独立隔离
  ├─ registry: ToolRegistry                  ← 共享
  ├─ abort: asyncio.Event                    ← 可共享或独立
  ├─ file_cache: FileStateCache              ← 深拷贝隔离
  ├─ emit_event / emit_ipc: Callable | None  ← 事件转发
  ├─ agent_id / agent_type: str | None       ← Agent 身份
  ├─ agent_depth: int                        ← 嵌套深度 (0=主循环, 最大=2)
  └─ critical_reminder: str | None          ← 每轮注入 (Verification Agent)
```

### 5.5 LoopState 状态机

```
LoopState
  ├─ transition: TransitionReason | None   ← 当前转换原因
  ├─ turn_count: int                      ← 循环迭代计数
  └─ _log: list[TransitionRecord]         ← 完整审计日志（含时间戳）

TransitionReason 枚举 (14 种):
  NEXT_TURN / COMPACT_RETRY / SURFACE_ERROR / STOP_HOOK_BLOCKING
  USER_INTERRUPT / TOOL_COMPLETED / MAX_TOKENS_ESCALATED
  MAX_TOKENS_RECOVERY / RECOVERY_INJECTED / STREAMING_DISCARD
  COMPACT_MICRO / COMPACT_FULL / COMPACT_BLOCKING / DONE
```

### 5.6 核心设计原则

- **单一状态源**：Store 是唯一运行时状态源，Settings 是持久化层
- **依赖注入**：工具和 QueryRunner 通过 ToolUseContext 间接访问 Store，不直接引用
- **隔离 + 选择性穿透**：子 Agent 默认隔离写操作，但任务注册始终穿透到根 Store
- **观察者模式**：Store 支持 subscribe(listener) 和 onChange 回调，实现响应式副作用
- **深拷贝安全**：snapshot() 返回 copy.deepcopy，防止外部修改污染内部状态

### 6.2 组装流程

```
build_system_prompt(cwd) → list[str]
  │
  ├─ [1] Identity           ← 静态，无参数
  ├─ [2] System             ← 静态，安全 & Markdown 规则
  ├─ [3] Actions            ← 静态，任务执行指导
  ├─ [4] Tool Guidelines    ← 静态，工具优先级
  ├─ [5] Agent Guidelines   ← 静态，Agent 使用规则
  ├─ [6] Coding Preferences ← 静态，编码风格
  ├─ [7] Output Efficiency  ← 静态，输出格式
  │
  ├─ ★ BOUNDARY MARKER ★    ← "__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__"
  │
  ├─ [8] Project Context    ← 动态，依赖 cwd
  └─ [9] Memory System      ← 动态，Memory 指令 + 当前索引 (memory/prompt.py)
```

### 6.3 静态/动态分割原理

**边界标记** `__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__` 是 Prompt Cache 的关键：

| 区域 | 特性 | Cache 行为 |
|------|------|-----------|
| 静态 (Section 1-7) | 无参数，跨会话相同 | 可缓存 (scope: ORG/GLOBAL) |
| 动态 (Section 8-9) | 依赖 cwd，每次会话变化 | 不缓存 (scope: NONE) |

`_split_system_prompt()` 在 `api/client.py:61` 按此标记拆分列表。

### 6.4 System Prompt 到 API 的完整路径

```
build_system_prompt(cwd)
  → [静态 sections...] + BOUNDARY + [动态 sections...]
          │
          ▼
QueryRunner.run()
  → 追加 format_system_context(git_info) 作为额外动态 section
          │
          ▼
stream_message()  (api/client.py:437)
  ├─ _split_system_prompt() → 拆分静态/动态
  ├─ Anthropic: build_system_prompt_blocks()
  │   → 静态块加 cache_control: {type: "ephemeral"}
  │   → 动态块不加 cache
  └─ OpenAI/DeepSeek: 合并为单字符串（无 Prompt Cache 支持）
```

### 6.5 子 Agent 的 System Prompt

| Agent | 文件 | 特点 |
|-------|------|------|

## 七、对话循环

### 7.1 QueryRunner 主循环流程

```
用户消息 → QueryRunner.run()
  │
  ├─ 构建 System Prompt (静态 + 动态 sections)
  ├─ 加载用户上下文 (NEXTCODE.md, Memory 索引, 日期)
  ├─ 将用户上下文前置到第一条用户消息
  ├─ 检查压缩需求 (如启用)
  │
  └─ FOR 每轮 (最大 50 轮):
       │
       ├─ [子 Agent 守卫] 估算 token，接近溢出则退出
       ├─ stream_message() → API 调用
       │    ├─ text_delta → yield 文本事件
       │    ├─ thinking_delta → yield 思考事件
       │    └─ tool_use blocks 收集
       │
       ├─ 构建助手消息 (Anthropic: content_blocks; OpenAI: content + tool_calls)
       │
       ├─ 无工具调用？
       │    ├─ 是 → 等待后台任务 → 如有结果注入则继续，否则 DONE 退出
       │    └─ 否 → 执行工具
       │
       └─ 有工具调用 → 执行工具:
            ├─ 流式模式: StreamingToolExecutor (并发分区)
            └─ 串行模式: 逐个执行 + 权限检查
            → 追加工具结果到 messages
            → 触发 Memory 提取检查
            → 记录 transition → 下一轮
```

### 7.2 循环退出条件

| 条件 | Transition | 位置 |
|------|-----------|------|
| 模型只返回文本（无 tool_use） | `DONE` | query.py:421 |
| 模型返回 tool_use blocks | `TOOL_COMPLETED` → 继续 | query.py:456/466 |
| 达到最大轮数 (50) | 循环自然退出 | query.py:255 |
| 循环前上下文 BLOCKING | 错误 + 返回 | query.py:225-233 |
| 子 Agent 上下文溢出 | 错误 + 中断 | query.py:268-273 |
| API 错误，无恢复策略 | `SURFACE_ERROR` + 返回 | query.py:371-373 |
| API 错误，已注入恢复 | `RECOVERY_INJECTED` → 继续 | query.py:359-362 |
| 后台 Agent 权限被拒 | 错误 + 中断 | query.py:470-478 |
| 流式错误，执行器丢弃 | `STREAMING_DISCARD` → 继续/恢复 | query.py:346-349 |
| 退出时仍有后台任务 | 注入结果 → 继续 | query.py:413-420 |

## 八、上下文管理

### 8.1 Token 预算（以 200K 模型为例）

| 级别 | 阈值 | 动作 |
|------|------|------|
| **Warning** | ~147K (auto-compact - 20K) | UI 黄色警告 |
| **Error** | ~147K | UI 红色警告 |
| **Auto-compact** | ~167K (effective - 13K) | 触发压缩 |
| **Blocking** | ~177K (effective - 3K) | 拒绝新查询 |

- `estimate_token_count()`: char/4 近似（不依赖 tiktoken）
- `get_effective_context_window()`: `context_window - min(max_output, 20K)`

### 8.2 三级压缩策略

NONE 是"无需压缩"的状态，不是压缩级别。实际压缩动作只有 3 级：

```
无需压缩(NONE) ──→ MICRO(清旧工具结果) ──→ FULL(模型摘要) ──→ BLOCKING(拒绝)
                      无可清除=升级FULL        断路器开=降级MICRO
```

| 级别 | 触发条件 (200K模型) | 机制 | 成本 | 信息损失 |
|------|-------------------|------|------|---------|
| NONE | < 147K | 无操作 | 无 | 无 |
| MICRO | 147K~167K | 清除旧 tool_result，保留最近 3 条 | 几乎为零 | 低 |
| FULL | 167K~177K | 模型生成 9 维结构化摘要 + 保留 5~20 条近期消息 | 一次 API 调用 | 中 |
| BLOCKING | >= 177K | 拒绝新查询，需手动 /compact | 无 | — |

### 8.3 FULL Compact 流程

1. 断路器检查（3 次连续失败停止）
2. 构建压缩提示词（对话历史序列化，tool_result 截断 500 字符）
3. 流式生成摘要：NO_TOOLS_PREAMBLE 防工具调用 + CoT then strip（剥离 analysis 节省 token）
4. 格式化摘要（9 维：主请求/关键概念/文件/错误/问题解决/用户消息/待办/当前工作/下一步）
5. 重建消息列表：[summary_message] + [recent_messages]
6. 修复 tool reference（移除孤立的 tool_use/tool_result 对）
7. 重新注入最近访问的文件内容（优先编辑 > 读取，最多 5 个，10K token 预算）

### 8.4 MICRO Compact 流程

1. 第一遍: 识别可压缩工具的 tool_use ID (Read, Glob, Grep, Bash, Edit, Write)
2. 第二遍: 找到对应 tool_result 位置，替换为 "[Old tool result content cleared]"
3. 保留最近 3 条工具结果不清理

### 8.5 Prompt Cache 机制

```
Anthropic KV Cache（仅 Anthropic 支持）

请求 1: [静态]--cache-->缓存前缀 [动态] [消息]--cache-->缓存到此处
请求 2: [静态]--命中0成本 [动态]--正常计费 [消息]--cache-->新缓存点
```

关键设计：
- **单 cache_control 每请求** — 在静态/动态边界标记，最大化缓存前缀
- **Latch 模式**: scope 和 TTL 在会话内只评估一次，永不翻转
- **Schema 缓存**: ToolRegistry 会话级 schema 缓存，保证字节一致性
- **字节一致性**: 缓存前缀必须在请求间完全匹配

### 8.6 用户上下文注入 (context/)

上下文不仅指压缩和 Cache，还包括三层数据注入到对话中：

```
src/next_code/context/
  system.py     -> 系统上下文（git branch/status，@lru_cache 缓存）
  user.py       -> 用户上下文（NEXTCODE.md + Memory 索引 + 日期，@lru_cache 缓存）
  nextcodemd.py -> NEXTCODE.md 文件解析
```

注入时机和位置：

| 上下文类型 | 内容 | 注入位置 |
|-----------|------|---------|
| **System Context** | git branch, git status, 平台信息 | 追加到 System Prompt 动态部分 |
| **User Context** | NEXTCODE.md 内容, Memory 索引, 当前日期 | 前置到第一条用户消息 |
| **NEXTCODE.md** | 项目级行为指南（如编码规范、项目约定） | 通过 User Context 注入 |

缓存策略：
- `get_system_context()`: `@lru_cache(maxsize=1)`，会话内缓存，`/clear` 命令时 `clear_system_context_cache()` 清除
- `load_user_context()`: `@lru_cache`，会话内缓存
- `prefetch.py`: REPL 启动时预热 `lru_cache`，避免首次请求延迟

### 8.7 FileStateCache（文件状态缓存）

`compact/file_cache.py` — 跟踪对话过程中访问和修改的文件：

```
FileStateCache
  + record_read(path, content)    记录读取的文件内容
  + record_write(path, content)   记录写入的文件内容
  + can_edit(path) -> (bool, str) 安全编辑守卫（防止编辑未完整查看的文件）
  + get_recently_accessed()       获取最近访问的文件（用于 Compact 后重新注入）

生命周期:
  - 主循环: 单例共享
  - 子 Agent: deep copy 隔离
  - Compact 后: 重新注入优先级 编辑文件 > 读取文件，按最近访问排序
```

安全编辑守卫（TOCTOU 防护）：
- 通过 `can_edit(path)` 检查文件是否曾被完整读取
- 防止模型在只看到文件部分内容时进行编辑（可能丢失未读部分）
- FileWriteTool 和 FileEditTool 在执行前都会检查

### 8.8 上下文管理完整流程图

```
用户消息进入 QueryRunner.run()
  |
  +-- 1. 构建 System Prompt
  |     build_system_prompt(cwd) -> [静态7sections] + BOUNDARY + [动态2sections]
  |     format_system_context(git_info) -> 追加动态 section
  |
  +-- 2. 注入用户上下文
  |     load_user_context() -> NEXTCODE.md + Memory索引 + 日期
  |     前置到第一条用户消息
  |
  +-- 3. 对话循环中
  |     工具执行 -> FileStateCache 记录读写
  |     每轮后检查 token 用量
  |
  +-- 4. 上下文压缩（如需要）
  |     MICRO: 清旧工具结果
  |     FULL: 摘要 + 重建 + FileStateCache 重新注入
  |     BLOCKING: 拒绝
  |
  +-- 5. Prompt Cache 优化
        静态部分命中缓存 -> 节省 token 成本
```

## 十二、任务系统

### 12.1 核心组件

| 组件 | 文件 | 职责 |
|------|------|------|
| `TaskRegistry` | `tasks/registry.py` | 单例注册表：注册/终止/驱逐/查询 |
| `TaskStateBase` | `tasks/types.py` | 任务状态数据结构 |
| `DiskTaskOutput` | `tasks/disk_output.py` | 异步写队列，5GB 上限 |
| `TaskOutputPoller` | `tasks/output_poller.py` | UI 驱动的输出轮询 (0.5s 间隔) |
| `StallWatchdog` | `tasks/stall_watchdog.py` | 交互式命令卡住检测 (45s 阈值) |

### 12.2 任务状态机

```
PENDING -> RUNNING -> COMPLETED
                   -> FAILED
                   -> KILLED
```

### 12.3 任务 ID 规则

- `b` + 8 hex chars -> Bash 后台任务 (如 b3k9m2x7p)
- `a` + 8 hex chars -> Agent 后台任务 (如 a7f2h8k3m)

### 12.4 后台任务创建流程

```
AgentTool._execute_background():
  1. 生成 task_id
  2. 创建 TaskStateBase(id, type=LOCAL_AGENT, status=RUNNING)
  3. 注册到 TaskRegistry
  4. asyncio.create_task(_run_and_complete) -> 异步执行，立即返回
  5. 返回 ToolResult(包含 task_id)
```

### 12.5 终止与驱逐

- `kill(task_id)`: 分发到 KillHandler，设置 status=KILLED
- `kill_for_agent(agent_id)`: 终止某 Agent 创建的所有任务（僵尸防护）
- 终端+已通知的任务在 60s 后自动驱逐
- `retain=True` 的任务保持可见，不自动驱逐

### 12.6 Agent 与 Task 的关系

- Agent != Task — 前台 Agent 运行无 Task 条目，后台 Agent 注册为 Task
- AgentTool 是桥梁：模型调用 Agent 工具 -> 决定前台/后台 -> 后台创建 TaskStateBase
- 语义去重防重复 + 并发控制(最大5个) + 嵌套检查(最大2层)
- 清理级联：kill_for_agent(agent_id) 在 Agent 退出时终止所有子任务

### 13.1 8 阶段决策管线

```
PermissionManager._check_inner() — 严格优先级:
```

## 十六、关键设计决策

1. **Click 而非 Typer**: Typer 底层是 Click，但 Click 更灵活，对子命令和 pre-action hook 支持更好
2. **双 UI 模式**: Rich REPL 零依赖开箱即用，Ink 前端提供更丰富交互，`--ink` 选项切换
3. **Unix Domain Socket IPC**: 比 stdin/stdout pipe 更可靠，支持双向通信，无需端口分配
4. **asyncio 全异步**: API 调用、工具执行、流式输出、IPC 通信全异步
5. **Pydantic 做 Tool schema**: 同时用于参数验证和生成 JSON Schema 给 API
6. **三级上下文压缩**: MICRO（零成本）-> FULL（API 调用）-> BLOCKING（保护），断路器防止无限重试
7. **静态/动态 Prompt 分割**: 优化 Prompt Cache 命中率，静态部分跨会话缓存
8. **ToolUseContext 解耦**: QueryRunner 通过 ToolUseContext 间接访问 Store，支持子 Agent 隔离和任务穿透
9. **Setting 配置**: JSON 格式，`~/.nextcode/.settings.json`（全局）+ `.nextcode/.settings.json`（项目级）
