# GG Bond Code 状态管理优化方案

## 一、现状总结

### 1.1 Claude Code 的三层状态架构（参考标杆）

Claude Code 采用**三层状态架构**，各层职责清晰、依赖方向单一：

| 层次 | 文件 | 生命周期 | 核心机制 |
|------|------|---------|---------|
| Session 全局 | `bootstrap/state.ts` | 进程级 | 模块级闭包单例 + getter/setter，无发布订阅 |
| AppState Store | `store.ts` + `AppStateStore.ts` + `AppState.tsx` | REPL 级 | 35 行极简 Store + `useSyncExternalStore` 桥接 React |
| ToolUseContext | `Tool.ts` | 每次交互级 | 运行时上下文容器，面向工具执行 |

关键设计亮点：
- **35 行自研 Store**：`getState/setState/subscribe` 三方法 API，零依赖，精确匹配 `useSyncExternalStore`
- **onChange 集中式副作用**：一次 `setState` 同时完成内存更新、持久化、UI 通知
- **Context 隔离 + 选择性共享**：子 Agent 默认隔离，`setAppStateForTasks` 始终穿透到根 Store
- **`Object.is` 引用相等性检查**：避免不必要的重渲染
- **函数式 `setState(prev => newState)`**：避免 stale closure
- **`DeepImmutable<T>` 类型包装**：编译期防止直接修改状态

### 1.2 GG Bond Code 的当前状态架构

GG Bond Code 目前有两套独立的全局状态机制：

| 机制 | 文件 | 用途 | 模式 |
|------|------|------|------|
| `_Store` 单例 | `state/store.py` | 运行时临时状态（cwd, model, messages） | 模块级单例，key-value 读写 |
| `_settings` 模块变量 | `config/settings.py` | 持久化配置（api_key, model, permissions） | 三层合并 + 点号路径访问 |

此外还有分散在组件实例中的状态：
- `REPL`：`show_thinking`, `show_tool_details`, `_last_interrupt_time`, `_current_task`
- `QueryRunner`：`model`, `family`, `registry`, `permissions`, `system_prompt`
- `PermissionManager`：`_allowed`, `_denied`, `_session_allowed`

## 二、当前问题分析

### 问题 1：Store 缺乏变更通知机制（严重）

**现状**：`_Store` 是一个纯 key-value 容器，`set()` 方法没有任何通知/订阅能力。

```python
def set(self, key: str, value: Any) -> None:
    self._data[key] = value  # 静默写入，无人知晓
```

**影响**：
- 无法实现响应式 UI 更新（当前项目是 CLI 所以暂时无感，但如果未来引入 TUI 框架如 Textual，这是硬伤）
- 无法实现 `onChange` 集中式副作用（Claude Code 的核心设计）
- 外部系统无法感知状态变更，只能轮询

**Claude Code 的做法**：Store 有 `subscribe` 方法 + `onChange` 回调，任何 `setState` 都会通知所有订阅者和执行副作用。

### 问题 2：Store 与 Settings 双轨并行，职责模糊（中等）

**现状**：`Store` 存运行时状态，`Settings` 存持久化配置，两者完全独立，但存在概念重叠：
- `model` 同时存在于 Store 和 Settings 中
- `Store` 中的 `model` 和 `Settings` 中的 `model` 可能不一致（CLI 参数 vs 配置文件 vs 环境变量）
- 没有统一的"单一状态源"概念

**Claude Code 的做法**：`bootstrap/state.ts` 存进程级不可变状态，`AppState` 存可变 UI 状态，两者通过 `onChange` 回调自动同步。模型切换时，一次 `setState` 同时更新内存状态 + 持久化到 settings.json + 通知 UI。

### 问题 3：状态变更无副作用处理，散落在各处（中等）

**现状**：状态变更后的副作用处理分散在各个调用点：
- `/model` 命令只读 Store 显示模型名，不更新 Settings
- 权限变更时 `PermissionManager._persist_allow()` 手动写文件
- `/clear` 命令直接操作 Store，不触发任何清理逻辑

**Claude Code 的做法**：所有副作用集中在 `onChangeAppState` 中处理，零遗漏。

### 问题 4：REPL 实例状态与全局 Store 混用（轻微）

**现状**：`REPL` 的 `show_thinking` 和 `show_tool_details` 是实例属性，但 `model` 和 `messages` 在全局 Store 中。这种不一致导致：
- `/clear` 命令需要同时操作 Store 和重建 `QueryRunner`
- 某些状态（如 thinking 开关）无法通过 Store 统一访问
- 未来如果需要持久化 UI 偏好，需要额外的机制

### 问题 5：Store 的 `snapshot()` 返回浅拷贝（轻微）

**现状**：
```python
def snapshot(self) -> dict[str, Any]:
    return dict(self._data)  # 浅拷贝，嵌套对象仍是引用
```

如果 `messages` 列表被外部代码直接修改（如 `messages.append(...)`），Store 内部的数据也会被改变，绕过了 `set()` 方法，破坏了状态管理的完整性。

**Claude Code 的做法**：`DeepImmutable<T>` 在类型层面禁止直接修改，`setState` 使用函数式更新确保每次都产生新引用。

### 问题 6：PermissionManager 直接引用 Settings 内部函数（轻微）

**现状**：
```python
from ..config.settings import get_setting, _load_json, _save_json
```

`PermissionManager` 直接导入并使用 `_load_json` 和 `_save_json` 这两个 settings 模块的私有函数，违反了封装原则。权限持久化应该通过 Settings 模块的公共 API 进行。

### 问题 7：缺少状态重置/清理机制（轻微）

**现状**：`_Store` 单例在进程生命周期内从不重置，`_settings` 只加载一次不重新加载。如果需要实现 session 切换或配置热重载，当前架构无法支持。

### 问题 8：QueryRunner 与 Store 耦合过紧（轻微）

**现状**：`QueryRunner.__init__` 直接调用 `Store()` 获取全局单例，并在 `run()` 中直接读写 Store 的 `messages`。这使得 `QueryRunner` 无法在隔离环境中运行（如子 Agent 场景）。

**Claude Code 的做法**：`ToolUseContext` 通过 `getAppState/setAppState` 函数间接访问 Store，子 Agent 可以替换为 no-op 或隔离版本。

## 三、优化方案

### 优化 1：为 Store 添加订阅和 onChange 机制（优先级：高）

**目标**：让 Store 具备变更通知能力，为响应式 UI 和集中式副作用奠定基础。

**方案**：

```python
class _Store:
    def __init__(self, on_change=None):
        self._data: dict[str, Any] = {}
        self._listeners: set[Callable] = set()
        self._on_change = on_change  # 可选的全局副作用回调

    def set(self, key: str, value: Any) -> None:
        old = self._data.get(key, _SENTINEL)
        if old is not value and old != value:  # 引用相等性检查
            self._data[key] = value
            self._on_change and self._on_change(key, value, old)
            for listener in self._listeners:
                listener(key, value, old)

    def subscribe(self, listener: Callable) -> Callable:
        self._listeners.add(listener)
        return lambda: self._listeners.discard(listener)
```

**收益**：
- 支持响应式 UI（未来接入 Textual 等框架）
- 支持集中式副作用处理
- 为 Store ↔ Settings 自动同步奠定基础

### 优化 2：统一 Store 与 Settings，建立单一状态源（优先级：中）

**目标**：消除 `model` 等字段的双源问题，让 Store 成为唯一的运行时状态源，Settings 作为持久化层。

**方案**：
- Store 初始化时从 Settings 加载默认值
- Store 的 `onChange` 回调负责将需要持久化的字段写回 Settings
- 移除 QueryRunner/REPL 中直接读取 Settings 的代码，统一从 Store 获取

```python
# 初始化时
def setup(cwd, model=None):
    store = Store(on_change=_sync_to_settings)
    store.set("cwd", cwd)
    store.set("model", model or get_setting("model", "deepseek-chat"))
    # ...

# onChange 自动同步
def _sync_to_settings(key, new_value, old_value):
    if key == "model":
        update_setting("model", new_value)  # 持久化
```

**收益**：
- 消除双源不一致问题
- 一次 `store.set()` 同时完成内存更新 + 持久化
- 与 Claude Code 的 `onChangeAppState` 模式对齐

### 优化 3：将 REPL 实例状态迁移到 Store（优先级：中）

**目标**：将 `show_thinking`、`show_tool_details` 等 UI 偏好状态统一到 Store 中。

**方案**：
```python
# setup.py 初始化
store.set("ui.show_thinking", False)
store.set("ui.show_tool_details", False)

# REPL 中使用
store = Store()
store.set("ui.show_thinking", not store.get("ui.show_thinking"))
```

**收益**：
- 状态访问方式统一
- 为 UI 偏好持久化奠定基础
- 未来可支持 `~/.ggbond/.settings.json` 保存 UI 偏好

### 优化 4：引入 ToolUseContext 运行时上下文容器（优先级：中）

**目标**：解耦 QueryRunner 与全局 Store 的直接依赖，为子 Agent 隔离奠定基础。

**方案**：
```python
@dataclass
class ToolUseContext:
    """运行时上下文容器 — 面向每次交互/工具执行"""
    get_state: Callable[[str], Any]
    set_state: Callable[[str, Any], None]
    permissions: PermissionManager
    registry: ToolRegistry
    abort: asyncio.Event
    # ...

# 主循环：连接真实 Store
ctx = ToolUseContext(
    get_state=store.get,
    set_state=store.set,
    permissions=permissions,
    registry=registry,
)

# 子 Agent：隔离的上下文
sub_ctx = ToolUseContext(
    get_state=store.get,       # 只读
    set_state=lambda k, v: None,  # no-op，防止干扰 UI
    permissions=isolated_permissions,
    registry=registry,
)
```

**收益**：
- QueryRunner 不再直接依赖全局 Store
- 支持子 Agent 隔离执行
- 与 Claude Code 的 `createSubagentContext` 模式对齐

### 优化 5：修复 snapshot() 浅拷贝问题（优先级：低）

**方案**：
```python
import copy

def snapshot(self) -> dict[str, Any]:
    return copy.deepcopy(self._data)
```

**收益**：防止外部代码通过引用直接修改 Store 内部数据。

### 优化 6：PermissionManager 通过 Settings 公共 API 持久化（优先级：低）

**方案**：在 `config/settings.py` 中添加 `update_setting(key, value)` 公共函数，`PermissionManager` 使用该函数而非直接调用 `_save_json`。

```python
# config/settings.py
def update_setting(key: str, value: Any) -> None:
    """Update a setting value and persist to project config."""
    # 深度设置嵌套值
    _set_nested(_settings, key, value)
    # 持久化到项目配置文件
    _save_project_settings()
```

**收益**：修复封装违规，统一持久化路径。

### 优化 7：添加 Store 重置能力（优先级：低）

**方案**：
```python
class _Store:
    def reset(self) -> None:
        """Reset store to empty state (for session switching / testing)."""
        self._data.clear()
        for listener in self._listeners:
            listener("__reset__", None, None)
```

**收益**：支持 session 切换、测试隔离。

## 四、优化优先级与实施路线

```
Phase 1（基础能力建设）:
  ├── 优化 1: Store 订阅 + onChange 机制
  └── 优化 5: snapshot() 深拷贝修复

Phase 2（架构对齐）:
  ├── 优化 2: Store ↔ Settings 统一
  └── 优化 3: REPL 状态迁移到 Store

Phase 3（扩展能力）:
  ├── 优化 4: ToolUseContext 运行时上下文
  └── 优化 6: PermissionManager 封装修复

Phase 4（锦上添花）:
  └── 优化 7: Store 重置能力
```

## 五、与 Claude Code 的差距总结

| 能力 | Claude Code | GG Bond Code | 差距 |
|------|------------|-------------|------|
| 变更通知 | `subscribe` + `onChange` | 无 | **缺失** |
| 集中式副作用 | `onChangeAppState` | 分散在各调用点 | **缺失** |
| React 桥接 | `useSyncExternalStore` | 不适用（CLI） | N/A |
| 状态不可变性 | `DeepImmutable<T>` | 无保护 | **缺失** |
| 子 Agent 隔离 | `createSubagentContext` | 无 | **缺失** |
| 选择性穿透 | `setAppStateForTasks` | 无 | **缺失** |
| 引用相等性检查 | `Object.is` | 无 | **缺失** |
| 函数式更新 | `setState(prev => next)` | 直接赋值 | **缺失** |
| 单一状态源 | AppState 统一 | Store + Settings 双轨 | **部分** |
| Selector 派生状态 | `selectors.ts` | 无 | **缺失** |

**核心差距**：GG Bond Code 的 Store 本质上是一个"全局字典"，缺少 Claude Code Store 的三个核心能力——**变更通知**、**集中式副作用**、**隔离与穿透**。这三个能力是状态管理从"能存取"到"能管理"的关键跨越。
