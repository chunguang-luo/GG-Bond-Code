# 上下文管理 - 概念详解与示例

> 本文档是 `06-上下文管理-实现计划.md` 的配套文档，用具体例子解释 Token 预算管理和多级压缩框架的核心概念，以及当前项目实现中的关键问题。

## 一、Token 预算管理

### 1.1 核心思想

**context window 不是全部可用的，需要层层预留，最终算出"安全线"在哪里。**

模型有一个 context window（如 200K tokens），看起来很大，但不能全部用来放对话历史——模型输出也需要空间，检测到需要压缩后当前 turn 还要继续执行，所以必须提前预留。

### 1.2 具体例子

假设模型 context window = **200K tokens**：

```
┌─────────────────────────────────────────────────────┐
│              200K Context Window                     │
│                                                       │
│  ┌─────────────────────────────────────────────────┐ │
│  │         180K = Effective Context Window          │ │
│  │    (留给输入消息用，扣掉 20K 输出预留)            │ │
│  │                                                   │ │
│  │  ┌─────────────────────────────────────────────┐ │ │
│  │  │    167K = Auto-Compact 阈值                  │ │ │
│  │  │    (再扣掉 13K 缓冲区)                       │ │ │
│  │  │                                               │ │ │
│  │  │  ┌─────────────────────────────────────┐     │ │ │
│  │  │  │  147K = Warning 阈值                 │     │ │ │
│  │  │  │  (再扣掉 20K 提前告警)               │     │ │ │
│  │  │  └─────────────────────────────────────┘     │ │ │
│  │  └─────────────────────────────────────────────┘ │ │
│  └─────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────┘
```

### 1.3 为什么每层都要预留？

| 预留 | 大小 | 原因 |
|------|------|------|
| **输出预留** 20K | 200K → 180K | 模型需要空间生成回复。compact 总结最大输出约 17K token（p99.99），预留 20K |
| **缓冲区** 13K | 180K → 167K | 检测到需要 compact 后，当前 turn 还要继续（工具调用、模型响应），留 13K 确保不爆 |
| **告警缓冲** 20K | 167K → 147K | 别等到临界才提醒，提前告警让用户有预期 |

### 1.4 四级响应

当 token 用量逐步攀升时：

```
用量 0 ──────→ 147K ────→ 167K ────→ 177K ────→ 180K
                │           │          │           │
           ⚠️ Warning    🔄 Auto     🔴 Error   🚫 Blocking
           UI黄色提示    Compact触发  UI红色提示  禁止新查询
                        (自动压缩)              必须 /compact
```

### 1.5 对比当前实现

当前 GG-Bond-Code **没有这个分层预算模型**，只有一个 `compact_threshold: 0.8` 的比例配置。

问题在于：

1. **不知道实际 window 多大** — 没有按模型区分 context window 大小
2. **没有输出预留** — 可能压缩后发现没空间生成回复
3. **没有缓冲区** — 检测到要 compact 时，当前 turn 可能已经超限
4. **没有分级告警** — 用户直到出问题才知道上下文满了

简单说，当前是从 80% 一刀切，Claude Code 是从 73.5% 开始逐级响应，每级都有明确的语义和动作。

## 二、多级压缩框架

### 2.1 核心思想

**不是一上来就用最重的手段，而是按压力等级逐步升级——能轻则轻，逼不得已才上重武器。**

#### 生活类比

想象手机存储满了：

```
存储快满时，你不会上来就删所有照片，而是：
  1. 先清理缓存（微信、浏览器）        ← 轻量，无损失
  2. 再删重复/模糊照片                 ← 中等，可接受损失
  3. 最后才把照片传电脑后全部删除       ← 重量级，最后手段
```

多级压缩就是这个思路应用在 context window 上。

### 2.2 具体例子

假设模型 context window = 200K，一段对话已经用了 **160K tokens**：

```
对话历史（160K tokens）:
  用户: 帮我重构 auth 模块
  助手: [思考...] 让我先看看代码结构
  工具: Read → auth.py 的内容（3000 tokens）
  工具: Read → middleware.py 的内容（2500 tokens）
  助手: 我看到了几个问题，让我搜索依赖...
  工具: Grep → 搜索结果（1800 tokens）
  助手: 现在开始重构，先编辑 auth.py...
  工具: Edit → 修改反馈（500 tokens）
  工具: Edit → 修改反馈（500 tokens）
  助手: 重构完成，跑一下测试...
  工具: Shell → 测试输出（2000 tokens）
  ... (更多对话)
```

### 2.3 第 1 级：Microcompact（清理旧工具结果）

**条件**：token 接近阈值但未超（如 160K，阈值 167K）

**动作**：不调用模型，直接把**旧的工具结果**替换为占位文本

```
Before Microcompact (160K):
  工具: Read → auth.py 的内容（3000 tokens）      ← 已消化
  工具: Read → middleware.py 的内容（2500 tokens）  ← 已消化
  工具: Grep → 搜索结果（1800 tokens）              ← 已消化
  工具: Edit → 修改反馈（500 tokens）                ← 刚做
  工具: Shell → 测试输出（2000 tokens）              ← 刚做

After Microcompact (153K，省了 7K):
  工具: Read → "[Old tool result content cleared]"  ← 5 tokens
  工具: Read → "[Old tool result content cleared]"  ← 5 tokens
  工具: Grep → "[Old tool result content cleared]"  ← 5 tokens
  工具: Edit → 修改反馈（保留）                      ← 最近的保留
  工具: Shell → 测试输出（保留）                     ← 最近的保留
```

**关键**：模型已经"消化"了旧工具结果并做出决策，那些大块内容后续价值递减，清理掉几乎无信息损失。

### 2.4 第 2 级：Full Compact（模型总结对话）

**条件**：Microcompact 不够用，token 超过 167K 阈值

**动作**：让模型自己总结之前的对话，用一段浓缩的总结替代整段历史

```
Before Full Compact (170K):
  [50 条消息，包括工具调用、代码、讨论...]

After Full Compact (30K):
  ┌─ 总结消息 ──────────────────────────────────────┐
  │ 1. 用户请求: 重构 auth 模块                      │
  │ 2. 关键文件: auth.py, middleware.py               │
  │ 3. 已完成: 将 session 验证提取为独立中间件         │
  │ 4. 测试状态: 全部通过                            │
  │ 5. 待办: 还需要更新 API 文档                     │
  │ 6. 当前工作: 准备提交 PR                         │
  └──────────────────────────────────────────────────┘
  + 最近 5 条消息（保持当前工作上下文）
```

**关键**：用一个 forked agent（maxTurns=1）执行总结，prompt 指导模型按 9 个维度输出，且禁止调用工具。

#### 9 维度总结详解

Full Compact 的 prompt 要求模型按以下 9 个维度进行结构化总结（来源：Claude Code 源码 `services/compact/prompt.ts`）：

```
1. Primary Request and Intent    — 用户的请求和意图
2. Key Technical Concepts        — 关键技术概念
3. Files and Code Sections       — 涉及的文件和代码片段
4. Errors and Fixes              — 遇到的错误和修复
5. Problem Solving               — 问题解决过程
6. All User Messages             — 所有用户消息（非工具结果）
7. Pending Tasks                 — 待完成的任务
8. Current Work                  — 当前进行的工作
9. Optional Next Step            — 可选的下一步
```

9 个维度覆盖了"模型继续工作所需知道的一切"：

```
知道"为什么来"   ──→  1. 用户意图
知道"讨论了什么" ──→  2. 技术概念 + 6. 所有用户消息
知道"碰了哪些"   ──→  3. 文件和代码
知道"踩了什么坑" ──→  4. 错误和修复 + 5. 解决过程
知道"还差什么"   ──→  7. 待办任务
知道"现在在干啥" ──→  8. 当前工作 + 9. 下一步
```

如果压缩后模型只知道最近几条消息，它不知道用户最初要干什么、改了哪些文件、碰过什么 bug——很容易重复劳动或偏离方向。9 个维度确保关键信息不丢。

#### 两个精巧设计

**设计 1：CoT 剥离（Chain-of-Thought 然后剥离）**

模型先在 `<analysis>` 标签中整理思路，再在 `<summary>` 标签中给出正式总结。后处理时 `formatCompactSummary()` 剥离 `<analysis>`，只保留 `<summary>`：

```
模型输出:
  <analysis>
    让我想想对话中发生了什么...                 ← 思考过程（提升总结质量）
    用户要重构 auth 模块...
    关键文件是 auth.py 和 middleware.py...
    测试已经通过了，但文档还没更新...
  </analysis>
  <summary>
  1. Primary Request: 重构 auth 模块
  2. Key Files: auth.py, middleware.py
  3. Completed: session 验证提取为独立中间件
  ...                                         ← 正式总结（注入后续上下文）
  </summary>

后处理:
  剥离 <analysis> → 只保留 <summary>
```

兼顾了总结质量和 token 经济性：让模型先深入思考提升质量，但不把思考过程注入后续上下文浪费 token。

**设计 2：NO_TOOLS_PREAMBLE（禁止工具调用前置声明）**

Compact prompt 开头有强力警告：

```
CRITICAL: Respond with TEXT ONLY. Do NOT call any tools.
- Tool calls will be REJECTED and will waste your only turn — you will fail the task.
```

原因是 compact 使用 `maxTurns: 1` 的 forked agent 执行——模型只有一次机会，如果尝试调用工具会被拒绝，白白浪费 API 调用。在 Sonnet 4.6 上这个问题的发生率从 0.01% 上升到了 2.79%，所以增加了这个前置强调。

### 2.5 第 3 级：Blocking（拒绝新查询）

**条件**：极度拥挤，用量 > 177K（effective - 3K）

**动作**：直接拒绝新查询，强制用户手动 `/compact`

```
🚫 Context window is nearly full. Please use /compact to compress the conversation.
```

**关键**：这是最后的安全阀。此时即使发请求也大概率 API 报错，不如直接拦截。

### 2.6 三级对比

```
         Microcompact          Full Compact           Blocking
         ───────────          ────────────           ────────
成本      几乎为零              一次 API 调用          无
信息损失   极小（旧工具结果）     中等（总结代替原文）    无（拒绝执行）
延迟      <1ms                 1-3秒                  无
触发条件   接近阈值              超过阈值               严重超限
自动化     自动                  自动                   必须手动
```

### 2.7 对比当前实现

当前 GG-Bond-Code **只有一种压缩**——简单截断保留最后 N 条消息：

```
当前: 50 条消息 → 硬保留最后 20 条 → 前 30 条直接丢弃

问题:
  ❌ 丢失用户原始请求（可能在最早的消息里）
  ❌ 丢失关键决策和错误修复过程
  ❌ 没有总结，模型不知道之前做了什么
  ❌ 不区分"可清理"和"必须保留"的内容
```

多级压缩的核心优势：**不是丢弃信息，而是浓缩信息**。Microcompact 清理的是低价值内容，Full Compact 是把高价值内容浓缩成总结——模型知道之前做了什么，只是不再有原始的完整代码/输出了。

## 三、当前实现的关键问题

### 3.1 `compact_threshold: 0.8` — 配了但没用

当前代码有**两条压缩路径**，都不用 `0.8`：

**路径 1：自动 compact（`query.py:121-133`）**

```python
if self._enable_compaction and len(messages) > self._max_messages:
    #                    ↑ 按消息条数判断       ↑ 硬编码 20
    should_compact, strategy = await should_compact_messages(
        messages, self.model,
        strategy=MessageCountStrategy(max_messages=self._max_messages),
        #                ↑ 按消息条数判断，不看 token
    )
    if should_compact:
        compacted_messages, reason = await strategy.compact(messages, self.model)
        # compact 做的事：messages[-20:]，只保留最后 20 条，前面的全丢
```

**路径 2：手动 `/compact`（`repl.py:269-277`）**

```python
elif cmd == "/compact":
    compacted = messages[-4:]    # 硬编码保留最后 4 条
    store.set("messages", compacted)
```

`compact_threshold: 0.8` 在 `settings.py` 里定义了，但**没有任何代码读取它**。

`TokenCountStrategy` 的接口虽然接受 `current_tokens` 参数，但 `should_compact_messages()` 调用时传的是 `0, 0`——等于**根本没有 token 计数**：

```python
# strategy.py:225
return await strategy.should_compact(messages, model, 0, 0), strategy
#                                              ↑    ↑
#                                    current_tokens  max_tokens
#                                    两个都是 0，根本没算
```

**总结**：`compact_threshold: 0.8` 是一个"看起来像那么回事"的配置项，实际效果为零。真正起作用的是 `len(messages) > 20`（硬编码消息条数）。它更像是当初设计时预留的"未来会用"的配置——原本意图可能是"当 token 用量达到 context window 的 80% 时触发 compact"，但因为代码里没有 token 计数能力，也没有 context window 的概念，所以一直空悬着没接上。

### 3.2 `max_tokens` 混淆了两个概念

当前代码的 `max_tokens` 管的是"模型输出上限"，缺少"模型输入上限（context window）"这个概念：

```
Claude Code 的模型                    GG-Bond-Code 的模型
─────────────────                     ──────────────────

context window = 200K                 context window = ???
(模型决定，代码查表获取)               (代码里根本没有这个概念)

effective window = 180K               max_tokens = 65536
(context_window - 20K输出预留)         (但这是"输出上限"，不是"输入上限")

auto-compact = 167K                   compact_threshold = 0.8
(effective - 13K缓冲)                 (配置了但没用上，实际用 message count)
```

**核心混淆**：

```
┌────────────────────────────────────────────────┐
│           Context Window (200K)                 │
│                                                 │
│   输入：system prompt + 对话历史 + 工具结果      │  ← 这是能装多少
│   输出：模型生成的回复                           │  ← max_tokens 控制这个
│                                                 │
└────────────────────────────────────────────────┘

当前代码只管了"输出上限"(max_tokens=65536→clamp到8192)
完全没有"输入上限"(context window)的概念
所以也就无法知道"对话历史什么时候快满了"
```

### 3.3 `_MAX_OUTPUT_TOKENS` 按家族而非按模型设限

用户配置了 `max_tokens: 65535`，但被 `_MAX_OUTPUT_TOKENS` clamp 到 8192——用户改配置改了个寂寞：

```python
# 用户配置
max_tokens = get_setting("context.max_tokens", 8192)   # → 65535

# 硬性上限
_MAX_OUTPUT_TOKENS: dict[str, int] = {
    "anthropic": 8192,
    "openai": 8192,
}

# 实际生效
max_tokens = min(max_tokens, _MAX_OUTPUT_TOKENS[family]) # min(65535, 8192) = 8192
```

问题是 `_MAX_OUTPUT_TOKENS` 按**模型家族**（anthropic / openai）设固定值，但同一家族内模型差异很大：

```
anthropic 家族：
  claude-haiku-4    → max_output = 8192
  claude-sonnet-4   → max_output = 16384  ← 被错误限制到 8192
  claude-opus-4     → max_output = 32768  ← 被错误限制到 8192

openai 家族（实际是 deepseek）：
  deepseek-chat     → max_output = 8192
  deepseek-reasoner → max_output = 16384  ← 被错误限制到 8192
```

Claude Code 的做法是按**具体模型名**查表获取 `maxOutputTokens`，而不是按家族一刀切。

### 3.4 问题汇总

| 问题 | 位置 | 影响 |
|------|------|------|
| `compact_threshold: 0.8` 未被使用 | `settings.py` → 无消费者 | 配置形同虚设 |
| 没有 token 计数 | `should_compact_messages()` 传 `0, 0` | 无法基于 token 用量决策 |
| 没有 context window 概念 | 全局 | 不知道输入空间有多大，无法算预算 |
| `max_tokens` 混淆输入/输出上限 | `client.py`, `settings.py` | 概念不清导致预算管理无从建起 |
| `_MAX_OUTPUT_TOKENS` 按家族而非模型 | `client.py:33-36` | 高端模型输出被错误限制 |
| 压缩策略只有简单截断 | `strategy.py` | 丢失关键上下文信息 |
| `/compact` 硬编码 4 条消息 | `repl.py:274` | 不可配置，信息损失大 |

## 四、200K 从哪来？

200K 是 **Claude 模型的 spec**，不是代码设置的。Claude Code 源码中是通过查表获取的：

```typescript
// Claude Code 原版
function getContextWindowForModel(model: string): number {
  // 查表：claude-sonnet-4 → 200000, claude-haiku → 200000, etc.
}
```

GG-Bond-Code 也需要建这个表，因为不同模型的 context window 差异很大：

```python
# 需要新建的映射
CONTEXT_WINDOWS: dict[str, int] = {
    "deepseek-chat": 64000,
    "deepseek-reasoner": 64000,
    "claude-sonnet-4-20250514": 200000,
    "claude-opus-4": 200000,
    "minimax-m2.7": 1000000,   # 1M context
    # ...
}
```

**总结**：当前代码的 `max_tokens` 管的是"模型输出上限"，缺少的是"模型输入上限（context window）"这个概念——而它才是 token 预算管理的起点。没有 context window 的大小，就无法计算 effective window，就无法算阈值，`compact_threshold: 0.8` 也就无从用起。

## 五、FileStateCache + Compact 后重建 + 告警体系

这三个机制是 P1 阶段要实现的核心功能，解决的是"压缩之外的三个盲区"问题。用一个完整场景串讲。

### 5.1 场景：用 GG Bond Code 重构一个项目

假设你正在用 GG Bond Code 对一个项目做大规模重构，对话已经进行了 40 轮。

### 5.2 FileStateCache — 解决"编辑了没看全的文件"

```
你：帮我读一下 src/api/client.py
助手：[用 Read 工具读取，文件有 2000 行]
      → 只读了前 500 行（因为太长被截断了）
      → FileStateCache 记录：
         client.py → { is_partial_view: true, offset: 1, limit: 500 }

你：把这个文件里的 stream_message 函数改一下
助手：[准备用 Edit 工具]
      → 检查 FileStateCache：client.py 是 is_partial_view=true
      → ⚠️ "我只读过这个文件的前 500 行，500 行之后的内容我没见过，
           直接编辑可能有风险（可能破坏我没看过的代码）"
      → 提示你：先完整读取文件再编辑
```

**没有 FileStateCache 的情况**：助手只看了文件前 1/4 就动手改，改出了 bug，因为它不知道 500 行后面有什么。

#### FileStateCache 的核心语义

| 字段 | 含义 |
|------|------|
| `content` | 读取时磁盘上的文件内容（用于 diff 比对） |
| `timestamp` | 读取时间（按时间排序恢复用） |
| `offset` / `limit` | 读了文件的哪些行 |
| `is_partial_view` | 是否只读了部分内容（截断注入标记） |

`is_partial_view` 是最关键的字段：

```
完整读取：is_partial_view = false → 安全编辑
部分读取：is_partial_view = true  → 可能不安全，需要警告
从未读取：FileStateCache 中无记录 → 必须先读取再编辑
```

#### 什么时候 is_partial_view 会是 true？

1. **用户指定了 offset/limit**：`Read client.py offset=100 limit=200` → 只读了 100-300 行
2. **文件太大自动截断**：文件有 5000 行，Read 工具只返回了前 2000 行
3. **Compact 后截断注入**：Full Compact 后恢复文件内容时，受 token 预算限制只注入了部分内容

### 5.3 Compact 后重建 — 解决"压缩后失忆"

40 轮对话后，上下文快满了，触发 Full Compact：

```
压缩前：
  消息历史 = 40 轮对话（约 15 万 tokens）
  FileStateCache 里记录了：client.py、query.py、system.py 等 12 个文件的状态
  当前正在修改的文件：client.py（刚读完，正在编辑中）

压缩后：
  消息历史 = 1 条模型总结 + 最近 3 轮对话（约 2 万 tokens）
  → 15 万 → 2 万，省了大量空间

但问题来了：
  ❌ 压缩前助手读过 client.py 的完整内容
  ❌ 压缩删掉了那些 Read 工具的返回结果
  ❌ 助手现在"失忆"了——不知道 client.py 长什么样
  ❌ 下次你让它编辑 client.py，它得重新读一遍

Compact 后重建：
  → 自动从 FileStateCache.get_recent(5) 拿到最近操作的 5 个文件
  → 重新注入到上下文中："最近操作的文件内容如下：\n[client.py 的内容]\n..."
  → 助手不需要重新读文件，直接继续编辑
  → Token 预算控制：最多注入 5 万 tokens（不会把刚压缩的空间又填满）
```

**没有重建的情况**：每次 compact 后助手都"失忆"，你要反复让它重新读文件，效率极低。

#### 重建的 token 预算控制

重建不是无脑把所有文件都塞回去——那样刚压缩的空间又被填满了：

```
POST_COMPACT_TOKEN_BUDGET = 50,000       # 重建总预算
POST_COMPACT_MAX_TOKENS_PER_FILE = 5,000 # 单个文件上限
POST_COMPACT_MAX_FILES_TO_RESTORE = 5    # 最多恢复 5 个文件

优先级排序：
  1. 最近修改的文件（正在编辑中的）
  2. 最近读取的文件
  3. Plan 文件（如果在 plan mode 中）
  4. Skill 内容（如果正在执行 skill）

预算内能装几个装几个，装不下的跳过（下次需要时再 Read）。
```

### 5.4 告警体系 — 解决"不知不觉就爆了"

```
第 30 轮：Token 使用 60%
  → 正常，无告警

第 35 轮：Token 使用 78%
  → 🟡 WARNING 告警："上下文接近上限，对话可能即将被压缩"

第 38 轮：Token 使用 85%
  → 🔴 ERROR 告警："上下文使用率过高，建议使用 /compact 手动压缩"

第 40 轮：Token 使用 92%
  → 自动触发 Full Compact
  → Compact 成功后：告警被抑制（因为 token 计数暂时不准确）
  → 不再显示告警，直到下次 microcompact 重新评估真实用量

极端情况：Token 使用 99%
  → 🚫 BLOCKING："上下文已满，无法继续。请使用 /compact 或 /clear"
  → 直接拒绝新的查询
```

**没有告警的情况**：对话突然被压缩，你不知道为什么；或者直接报错"上下文满了"，你措手不及。

#### 告警抑制机制

Compact 成功后需要一个"冷静期"，因为：

```
Compact 前：token 计数 = 170K → 触发 WARNING/ERROR
Compact 后：消息被总结 → 但我们不知道总结后实际多少 token
           → 需要等下一轮 API 请求才能知道真实 token 数

如果 Compact 后立即重新评估：
  → 可能还是显示 WARNING（因为 estimate 不精确）
  → 用户会困惑："刚压缩了怎么还是满的？"

所以：Compact 成功 → 抑制告警 → 下次 microcompact 清除抑制 → 恢复真实告警
```

### 5.5 三个机制如何协同工作

```
对话进行中
    │
    ├── FileStateCache 持续追踪：每个文件读了多少、是否截断
    │   │
    │   └── Edit 工具调用时检查 can_edit()
    │       → is_partial_view=true → 警告用户
    │       → is_partial_view=false → 正常编辑
    │
    ├── 告警体系 持续监控：当前 token 用量到了哪个级别
    │   │
    │   ├── < 60% → 安静
    │   ├── 60-80% → 🟡 提醒
    │   └── > 80% → 自动 Microcompact（清理旧工具结果）
    │
    └── 达到 auto-compact 阈值
        │
        ├── 1. 保存 FileStateCache 快照（记住哪些文件最近在读）
        ├── 2. 执行 Full Compact（模型总结对话）
        ├── 3. 用快照重建上下文（重新注入最近文件内容）
        ├── 4. 抑制告警（避免误报）
        └── 5. 后续 microcompact 清除抑制（恢复真实告警）
```

**一句话总结**：FileStateCache 防止"瞎改没看全的文件"，Compact 后重建防止"压缩后失忆要重新读"，告警体系防止"不知不觉上下文爆了"。三者协同，让上下文管理既有安全守卫，又有信息恢复，还有用户感知。
